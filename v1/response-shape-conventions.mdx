---

`/v1/` responses follow a small set of structural rules. Knowing them means you can predict
the shape of an endpoint you haven't called yet.

| Rule | Example |
|---|---|
| Date ranges are a `period` object | `"period": {"start": "2013-04-01", "end": "2017-01-31"}` |
| Money values are an `amount` object | `"amount": {"net": 327.0, "tax": 0.0, "gross": 327.0}` |
| Repeating values are an array | `"hierarchy": ["17 10 01", "17 10 01.06"]` |
| Coded values carry code and label together | `"exclusivity": {"code": 0, "label": "Vorschlag"}` |
| ID fields are flat, always | `property_id`, `account_id`, `floor_area_id` are never nested, in any table |

The last rule is the one guarantee that holds everywhere: the ID fields you use to
cross-reference records between endpoints stay at the top level of every response, so joins
across endpoints never depend on the surrounding structure.

<Warning>
  Objects always carry all their keys; a missing value is `null`. A `period` with no end date
  comes back as `{"start": "2020-06-01", "end": null}`, one with neither bound as
  `{"start": null, "end": null}`. Before, such keys were left out entirely (see the
  [changelog](/changelog)). So check for values rather than for an empty object or for both
  bounds: on `Contracts.service_contracts`, for example, most rows have only
  `contract_period.start`. The same applies to code/label pairs, where `label` can be `null`
  for a present `code`. This applies to the category endpoints: `/v1/raw` returns source data
  unchanged, so keys can still be missing there.
</Warning>

<Note>
  Not every table applies all of these rules yet. Each [data model](/v1/data-model/overview)
  page documents the actual structure of its tables, and the **API Reference** tab always
  shows what an endpoint returns today.
</Note>
