This glossary defines field names that appear on more than one `/v1/` table documented in
the [v1 Data Model](/v1/data-model/overview). Use it as a quick reference when joining
across the `/v1/` tables — several of these fields carry different meanings on different
tables, which is exactly why they're worth checking here first.

| Field | Type | Description |
| --- | --- | --- |
| `property_id` | string | Unique property identifier; primary join key across every `/v1/` table, and it resolves against `properties` on all of them. |
| `person_id` | string or integer | Identifies a tenant or contact person. `booking_header`, `booking_positions`, `tenants`, and `contract_debit_diffs` share one identifier space, scoped per property — join on `property_id` **and** `person_id` together, and cast `booking_positions.person_id` (a number) to a string first. `notifications.person_id` is a separate sequence from another subsystem and does not belong to that space. |
| `floor_area_person_id` | string | Identifies a specific tenancy. Appears on `tenants`, `contract_debits`, `contract_ends`, and `index_rent`, and is the same underlying value and the same type on all four — join across them directly on this field, no per-property scoping and no cast needed. It's composed of `floor_area_id` and `person_id`, but use the field as given rather than deriving it yourself. |
| `creditor_id` | string | Identifies a creditor (vendor or service provider). References `Stakeholder.creditor` — see the [Stakeholder field reference](/v1/data-model/stakeholder). Unreliable on `projects`; see the [Operations field reference](/v1/data-model/operations). |
| `floor_area_id` | integer or string | References [`Property.property_structure`](/v1/data-model/property#property_structure). Appears on `technical_objects`, `tenants`, `contract_ends`, and `property_structure` itself as an integer — except on `contract_debits`, where it's a string; cast before joining. |
| `account_id` | integer or string | Internal ledger account identifier. One consistent join key on `accounts`, `booking_positions`, `budgets`, and `contract_debit_diffs` — all join to `accounts.account_id`; see the [Accounting field reference](/v1/data-model/accounting). Two tables reuse the name for something else: `property_structure.account_id` is a string business key on structure nodes (see the [Property field reference](/v1/data-model/property#property_structure)), and `index_rent.account_id` is a debit-type code matching `contract_debits.debit_type.code` — an integer like the ledger key, but from a different value space, so a join against `accounts` silently returns nothing (see the [Contracts field reference](/v1/data-model/contracts#index_rent)). |
| `account_number` | string | Human-readable account number on `accounts` and `budgets` — don't confuse it with `account_id` above, which is a different (internal) value. |
| `account_name` | string | **Ambiguous across tables — not one concept.** On `accounts`, the ledger account's name. On `depreciation/assets`, the accounting basis a depreciation record is booked under (e.g. `"Handelsrecht"` vs. `"Steuerrecht"`). On `property_structure`, the display name of the structure node (cost centre or unit name). Three unrelated concepts sharing one field name. |
| `period` | object | **Ambiguous across tables — not one concept.** On `booking_positions`, the booking period (`{start, end}`) for a posting. On `contract_ends`, the lease term (`{start, end}`), where `end` is the option-adjusted effective end date, not the raw contractual end date. |
| `property_structure_account_id` | string | Foreign key into [`Property.property_structure`](/v1/data-model/property#property_structure), matching its `account_id`. On `booking_header` and `booking_positions` it's always populated and is the only way to resolve a booking down to a unit. On `technical_objects` it's the fallback for rows without a `floor_area_id`. |
| `cost_center_id` | string | Cost centre reference. Appears on `notifications` and `projects`; no `/v1/` cost-centre endpoint exists yet to resolve it against. |
| `booking_date` | date | ISO-8601 date of the ledger booking. Appears on `booking_header` and `booking_positions`. |
| `dms_link` | string | Link to the related document in the document management system, if attached. Appears on `booking_header`, `creditor`, `properties`, `property_structure`, and `tenants`. |

<Note>
  Fields prefixed with `sk_` are internal surrogate keys. None of the tables documented under
  `/v1/` currently expose one, but if you encounter one via the **API Reference** tab, don't
  rely on it as a stable identifier.
</Note>
