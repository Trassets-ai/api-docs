---
title: "Delta Sync nutzen, um geänderte Tabellen effizient zu erkennen"
description: "/changes mit dem Parameter since und ETags abfragen, um unnötige Abrufe zu vermeiden und zu erkennen, welche Tabellen seit dem letzten Sync neue Daten haben."
sidebarTitle: "Delta Sync"
---

Finde heraus, welche Tabellen seit deinem letzten Sync aktualisiert wurden, ohne jeden Endpunkt abzurufen. Der Endpunkt `GET /changes` der Data API liefert Metadaten für geänderte Tabellen und unterstützt bedingte Requests über ETag, um Polling zu überspringen, wenn nichts Neues vorliegt.

<Tip>
  Frage `/changes` alle 15–60 Minuten ab. Der zugrunde liegende Sync läuft als täglicher Batch — häufigeres Abfragen liefert keine neueren Daten, sondern verbraucht nur mehr von deinem 500-Requests/h-Budget. Kombiniere das mit dem `since`/ETag-Muster weiter unten, damit unveränderte Abfragen günstig bleiben.
</Tip>

<Note>
  Mit einem `transformed`-Key listet `/changes` nur Tabellen innerhalb der Kategorien und Tabellen des Keys; Tabellen ohne Kategorie erscheinen nie, und `?category=X` außerhalb des Keys liefert 403. Ein `raw`-Key sieht alle Tabellen — siehe [Key-Typen](/de/authentication#key-typen).
</Note>

<Steps>
  <Step title="Geänderte Tabellen abfragen">
    Sende einen `GET`-Request an `/changes` mit einem ISO-8601-Zeitstempel `since` (UTC, z. B. `…Z`). Ein Offset wie `+02:00` wird nach UTC umgerechnet; schreibe das `+` in der Query-String als `%2B`, sonst wird es als Leerzeichen gelesen und die Anfrage scheitert mit 400. Die Antwort listet jede Tabelle auf, deren `last_sync_at` nach diesem Zeitstempel liegt, inklusive der zugehörigen Endpunkt-URL. Eine hier gelistete Tabelle musst du **vollständig** neu abrufen — `/changes` meldet geänderte Tabellen, keine geänderten Zeilen. `endpoint_url` zeigt auf einen Pfad, den dein Schlüssel aufrufen darf: `/{category}/{table}` für Kunden der unversionierten API, `/v1/{category}/{table}` für reine v1-Kunden, `/raw/{table}` für Raw-Tabellen. Für dein Konto gesperrte Raw-Tabellen werden nicht gelistet. Mit dem optionalen Parameter `category` (z. B. `category=property`) werden nur Tabellen dieser Kategorie zurückgegeben.

    ```bash
    curl -s "https://api.trassets.ai/changes?since=2026-07-01T00:00:00Z" \
      -H "X-API-Key: $TRASSETS_API_KEY"
    ```

    Beispiel-Antwort:

    ```json
    [
      {
        "table_name": "properties",
        "last_sync_at": "2026-07-07T06:00:00",
        "category": "property",
        "api_table_name": "properties",
        "endpoint_url": "/property/properties"
      },
      {
        "table_name": "sollart",
        "last_sync_at": "2026-07-07T06:05:00",
        "endpoint_url": "/raw/sollart"
      }
    ]
    ```
  </Step>
  <Step title="Nur geänderte Tabellen abrufen">
    Rufe für jedes von `/changes` zurückgegebene Element nur den entsprechenden Endpunkt ab. Überspringe jede Tabelle, die nicht in der Antwort enthalten ist. So vermeidest du unnötigen Datentransfer und schonst dein Rate-Limit-Budget von 500 Req/h.
  </Step>
  <Step title="Bedingtes GET bei nachfolgenden Abfragen nutzen">
    Speichere den `ETag`-Header aus der ersten erfolgreichen `/changes`-Antwort. Sende ihn bei deiner nächsten Abfrage als `If-None-Match` zurück.

    ```bash
    curl -s "https://api.trassets.ai/changes?since=2026-07-01T00:00:00Z" \
      -H "X-API-Key: $TRASSETS_API_KEY" \
      -H "If-None-Match: \"abc123\""
    ```

    Der `ETag` hängt auch von `since` und `category` ab; bewahre ihn deshalb zusammen mit dem `since` auf, für das er ausgestellt wurde. Wenn sich seit der Ausstellung des ETag keine Tabellen geändert haben, liefert die API `304 Not Modified` mit leerem Body und überspringt die Datenbankabfrage. Der Request zählt trotzdem auf dein Rate-Limit.
  </Step>
  <Step title="Den Parameter since fortschreiben">
    Speichere nach einem erfolgreichen Sync das höchste `last_sync_at` aus der `/changes`-Antwort und nutze es als Wert für `since` bei der nächsten Abfrage. So entsteht ein gleitendes Zeitfenster, sodass jeder Lauf nur das Intervall seit dem vorherigen Lauf bewertet. Ist die Antwort leer, bleibt das bisherige `since` bestehen.

    Nimm dafür nicht deine eigene Uhr. Client- und Serveruhr weichen voneinander ab, und eine Tabelle, die kurz vor deinem Zeitstempel fertig synchronisiert wurde, würde in keiner späteren `/changes`-Antwort mehr auftauchen.
  </Step>
  <Step title="Vollständiges Python-Beispiel">
    Ein vollständiger Poller, der den Zeitstempel `since` und den `ETag` zwischen den Läufen
    verfolgt und nur Tabellen verarbeitet, die sich tatsächlich geändert haben. Erfordert das
    Paket [`requests`](https://pypi.org/project/requests/).

    ```python poll_changes.py
    import os

    import requests

    API_KEY = os.environ["TRASSETS_API_KEY"]
    BASE_URL = "https://api.trassets.ai"
    HEADERS = {"X-API-Key": API_KEY}


    def poll_changes(since: str, etag: str | None = None):
        """Poll /changes and return (changed_tables, new_etag, new_since).

        changed_tables is an empty list on a 304 Not Modified response, and
        new_since stays unchanged then.
        """
        headers = dict(HEADERS)
        if etag:
            headers["If-None-Match"] = etag

        resp = requests.get(
            f"{BASE_URL}/changes", headers=headers, params={"since": since}, timeout=30
        )

        if resp.status_code == 304:
            return [], etag, since

        resp.raise_for_status()
        changed = resp.json()
        if not changed:
            return [], resp.headers.get("ETag"), since
        # last_sync_at is UTC without a suffix; the API expects it with "Z"
        new_since = max(t["last_sync_at"] for t in changed) + "Z"
        return changed, resp.headers.get("ETag"), new_since


    if __name__ == "__main__":
        since = "2026-07-01T00:00:00Z"
        etag = None

        changed, etag, since = poll_changes(since, etag)
        for table in changed:
            print(f"Changed: {table['table_name']} -> {table['endpoint_url']}")
        if not changed:
            print("No changes since last poll.")

        # Persist `since` and `etag` and pass them into the next scheduled run.
    ```
  </Step>
</Steps>

<Warning>
  Der Parameter `since` darf nicht älter als 120 Tage sein. Requests mit einem Zeitstempel jenseits dieses Rückblickfensters liefern einen Fehler. Führe einen vollständigen Tabellen-Refresh aus, wenn dein letzter erfolgreicher Sync mehr als 120 Tage zurückliegt.
</Warning>
