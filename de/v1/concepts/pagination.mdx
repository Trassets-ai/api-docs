---

Jeder Listen-Endpunkt unter `/v1/` — Category wie Raw — nutzt Cursor-Pagination. Die Pagination-Felder stehen im Response-Body. Es gibt keine Pagination-Header und keinen `offset`-Parameter; ein Request mit `offset` liefert `400 Bad Request`.

## Request

<ParamField query="limit" type="integer" default="1000">
  Zeilen pro Seite. Maximal 100.000 bei Category-Endpunkten, 10.000 bei Raw-Endpunkten.
</ParamField>

<ParamField query="cursor" type="string">
  Der `next_cursor`-Wert aus der vorherigen Antwort, unverändert übergeben. Für die erste Seite weglassen.
</ParamField>

Behalte innerhalb eines Laufs auf jeder Seite dieselben Filterparameter bei.

## Response

```json
{
  "data": [ { "…": "…" } ],
  "count": 1000,
  "next_cursor": "eyJjb2wiOiAi…",
  "total": 167953
}
```

<ResponseField name="data" type="array">
  Die Zeilen dieser Seite.
</ResponseField>

<ResponseField name="count" type="integer">
  Anzahl der Zeilen in `data`.
</ResponseField>

<ResponseField name="next_cursor" type="string | null">
  Opaker Cursor für die nächste Seite. `null`, wenn keine Zeilen mehr folgen. Auf Raw-Endpunkten trägt jede volle Seite einen Cursor, der letzte Request kann deshalb ein leeres `data`-Array liefern.
</ResponseField>

<ResponseField name="total" type="integer">
  Category-Endpunkte: Zeilen, die ab der Cursor-Position zur Abfrage passen; auf der ersten Seite alle passenden Zeilen. Raw-Endpunkte: Zeilenzahl der Tabelle aus dem letzten abgeschlossenen Sync.
</ResponseField>

Raw-Endpunkte (`/v1/raw/{table_name}`) ergänzen den Body um `table_name` und senden einen `X-Snapshot-At`-Header mit dem Zeitstempel des letzten erfolgreichen Syncs der Tabelle.

Eine Raw-Tabelle, deren `status` in `GET /v1/raw/tables` nicht `synced` ist, liefert `400 Bad Request` mit `RAW table '…' is not ready (status: …)`. Versuche es nach dem nächsten Sync erneut; ein sofortiger Neustart bei der ersten Seite liefert denselben Fehler.

## Beispiel

```bash
# Erste Seite
curl -G "https://api.trassets.ai/v1/property/properties" \
  -H "X-API-Key: $TRASSETS_API_KEY" \
  -d "limit=1000"

# Nächste Seite: next_cursor aus der vorherigen Antwort übergeben
curl -G "https://api.trassets.ai/v1/property/properties" \
  -H "X-API-Key: $TRASSETS_API_KEY" \
  -d "limit=1000" \
  -d "cursor=eyJjb2wiOiAi…"
```

Wiederhole das, bis `next_cursor` `null` ist. Eine vollständige Python-Schleife steht unter [Incremental Sync](/de/v1/guides/incremental-sync).

## Reihenfolge und Stabilität

**Category-Endpunkte:** Die Zeilen sind nach der Sortierspalte der Tabelle (oder dem Primärschlüssel) sortiert, `NULL`-Werte zuletzt, bei Gleichstand entscheidet die interne Zeilenposition — Zeilen mit gleichem Wert werden weder übersprungen noch doppelt geliefert. Tabellen ohne Sortierspalte und Primärschlüssel werden allein nach Zeilenposition paginiert.

**Raw-Endpunkte:** Die Zeilen sind nach der Schlüsselspalte der Tabelle sortiert — dem Feld `primary_key` in `GET /v1/raw/tables` —, `NULL`-Werte zuletzt, bei Gleichstand entscheidet die interne Zeilenposition; keine Zeile wird übersprungen oder doppelt geliefert. Tabellen ohne Schlüsselspalte werden allein nach Zeilenposition paginiert.

<Warning>
  Ein Cursor gilt nur innerhalb eines Sync-Laufs. Jeder Sync lädt die Tabellen vollständig neu (wann Syncs laufen: siehe [Sync-Zyklus](/de/concepts/sync-cycle)); danach verschieben sich Zeilenpositionen. Wird eine Tabelle während deiner Pagination neu synchronisiert, liefert die nächste Anfrage mit einem Cursor von davor `409 Conflict` (`Table was re-synced during pagination; restart without cursor.`) — starte dann neu ab der ersten Seite ohne `cursor`. So mischt ein Lauf nie Zeilen aus zwei Syncs. Speichere `next_cursor` nicht zwischen Läufen — starte jeden Lauf mit der ersten Seite. Ein veränderter Cursor oder einer aus einem älteren Format liefert `400 Bad Request`; starte dann ebenfalls bei der ersten Seite.
</Warning>
