Die v1-Property-Domäne umfasst aktuell drei Tabellen: `properties`,
`property_creditor_services` und `technical_objects`.

<Note>
  `property_structure` ist noch nicht live unter `/v1/` — nutze vorerst das unversionierte
  [`Property.property_structure`](/de/data-model/property#property_structure).
</Note>

## properties

`GET /v1/property/properties` — eine Zeile pro Objekt.

<ResponseField name="property_id" type="string" required>
  Eindeutige Objekt-ID. Hier ein String, während die unversionierte Entsprechung
  (`Property.properties.property_id`) ein Integer ist.
</ResponseField>

<ResponseField name="entrances" type="string[]">
  Zugänge / Straßenadress-Komponenten des Gebäudes. Ersetzt die unversionierten
  durchnummerierten Spalten `entrance_1`–`entrance_5` durch ein einzelnes Array, gemäß den
  [Response-Shape-Konventionen](/de/v1/response-shape-conventions).
</ResponseField>

<ResponseField name="mandate_period" type="object">
  Verwaltungsmandats-Zeitraum — `{start, end}` (Datumsstrings). Ersetzt die unversionierten
  getrennten Felder `begin_mandate`/`end_mandate`.
</ResponseField>

<ResponseField name="accounting_property_id" type="string">
  Verifizierter Join-Key auf die buchhalterische Objektreferenz. Umbenannt aus einem
  Sync-Pipeline-Feld der unversionierten Tabelle; das exakte Zieltabellenschema ist noch
  nicht anderswo dokumentiert — als stabilen Identifikator behandeln, ohne weitere Struktur
  daraus abzuleiten.
</ResponseField>

<ResponseField name="obj_name" type="string">
  Objektname.
</ResponseField>

<ResponseField name="postcode" type="string">
  Postleitzahl.
</ResponseField>

<ResponseField name="adr_city" type="string">
  Stadt-Komponente der Objektadresse.
</ResponseField>

<ResponseField name="city" type="string">
  Stadt. Zu unterscheiden von `adr_city` — welches der beiden Felder für die Anzeige zu
  nutzen ist, ist mit dem Quellsystem nicht geklärt.
</ResponseField>

<ResponseField name="country" type="string">
  Land.
</ResponseField>

<ResponseField name="construction_year" type="integer">
  Baujahr des Objekts.
</ResponseField>

<ResponseField name="longitude" type="number">
  Längengrad.
</ResponseField>

<ResponseField name="latitude" type="number">
  Breitengrad.
</ResponseField>

<ResponseField name="state_name" type="string">
  Bundesland.
</ResponseField>

<ResponseField name="use_type" type="string">
  Nutzungsart des Objekts.
</ResponseField>

<ResponseField name="property_type" type="string">
  Objekttyp.
</ResponseField>

<ResponseField name="tax_model" type="string">
  Für das Objekt angewendetes Steuermodell.
</ResponseField>

<ResponseField name="dms_link" type="string">
  Link zum Objektdokument im Dokumentenmanagementsystem, falls vorhanden.
</ResponseField>

## property_creditor_services

`GET /v1/property/property_creditor_services` — welcher Kreditor welche Dienstleistung für
ein Objekt erbringt, und ob diese Zuordnung exklusiv ist.

<ResponseField name="property_id" type="string" required>
  Eindeutige Objekt-ID. Hier ein String, während die unversionierte Entsprechung ein
  Integer ist.
</ResponseField>

<ResponseField name="creditor_id" type="string" required>
  Referenziert `Stakeholder.creditor` — siehe die
  [Stakeholder-Feldreferenz](/de/v1/data-model/stakeholder). Hier ein String, während die
  unversionierte Entsprechung ein Integer ist.
</ResponseField>

<ResponseField name="service" type="string">
  Dienstleistungsname (z. B. Reinigung, Aufzugswartung).
</ResponseField>

<ResponseField name="exclusivity" type="object">
  Ob der Kreditor eine exklusive Zuordnung für diese Dienstleistung bei diesem Objekt hat —
  `{code, label}` (z. B. `{"code": 1, "label": "Exklusiv"}`). Ersetzt das unversionierte
  reine String-Feld, gemäß den
  [Response-Shape-Konventionen](/de/v1/response-shape-conventions).
</ResponseField>

## technical_objects

`GET /v1/property/technical_objects` — technische/gemessene Installationen an einem Objekt
(Aufzüge, Heizungsanlagen, Zähler und ähnliche Anlagen).

<Note>
  `technical_objects` stellt im Live-v1-Schema über 20 Felder bereit (Gewährleistungs-,
  Inspektions- und Wartungsdaten und -Flags). Diese Seite dokumentiert nur die wichtigsten
  Identifikations-, Verknüpfungs- und umgeformten Felder — die vollständige, automatisch
  generierte Feldliste findest du im Tab **API Reference**.
</Note>

<ResponseField name="to_id" type="integer" required>
  ID des technischen Objekts.
</ResponseField>

<ResponseField name="property_id" type="integer" required>
  Eindeutige Objekt-ID.
</ResponseField>

<ResponseField name="floor_area_id" type="integer">
  Fläche, in der das technische Objekt installiert ist, falls zutreffend.
</ResponseField>

<ResponseField name="creditor_id" type="integer">
  Für das Objekt verantwortlicher Wartungskreditor. Referenziert `Stakeholder.creditor` —
  siehe die [Stakeholder-Feldreferenz](/de/v1/data-model/stakeholder).
</ResponseField>

<ResponseField name="to_nr" type="string">
  Nummer des technischen Objekts.
</ResponseField>

<ResponseField name="name" type="string">
  Objektname.
</ResponseField>

<ResponseField name="type" type="string">
  Objekttyp.
</ResponseField>

<ResponseField name="built_date" type="date">
  Installations-/Baudatum.
</ResponseField>

<ResponseField name="is_meter" type="boolean">
  Ob dieses Objekt einen Zähler repräsentiert.
</ResponseField>

<ResponseField name="property_structure_account_id" type="string">
  Fremdschlüssel auf `Property.property_structure`. Neu in v1 und bedingt befüllt: nur bei
  Zeilen ohne `floor_area_id` gesetzt (aktuell eine kleine Minderheit); sonst überall
  `null`, dort bleibt `floor_area_id` der Join-Key.
</ResponseField>

<Note>
  Es gibt keinen separaten Endpunkt für Zählerstände. Eine `technical_objects`-Zeile kann
  einen Zähler repräsentieren, aber dieser Endpunkt liefert nur die Stammdaten des Objekts
  (Typ, Standort, verantwortlicher Kreditor) — keine Verbrauchsablesungen.
</Note>
