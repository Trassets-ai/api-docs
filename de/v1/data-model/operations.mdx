Die v1-Operations-Domäne umfasst zwei Tabellen: `notifications` und `projects`.

<Note>
  `offers` und `orders` haben noch keinen `/v1/`-Endpunkt — bis dahin über den
  unversionierten Pfad abrufen, siehe das [vollständige Datenmodell](/de/data-model/operations).
</Note>

## notifications

`GET /v1/operations/notifications` — Instandhaltungs- und Schadensmeldungen.

<ResponseField name="report_id" type="integer" required>
  Eindeutige Meldungs-ID.
</ResponseField>

<ResponseField name="property_id" type="string" required>
  Eindeutige Objekt-ID.
</ResponseField>

<ResponseField name="report_nr" type="string">
  Lesbare Meldungsnummer. Nicht eindeutig — dieselbe Nummer kommt bei verschiedenen Meldungen
  vor, auch innerhalb eines Objekts. `report_id` ist das einzige Feld, das eine Zeile
  identifiziert.
</ResponseField>

<ResponseField name="report_name" type="string">
  Kurzbezeichnung der Meldung. Freitext, auf jeder Zeile befüllt.
</ResponseField>

<ResponseField name="technical_object_id" type="integer">
  Technisches Objekt, das die Meldung betrifft. Referenziert
  `Property.technical_objects.to_id`.
</ResponseField>

<ResponseField name="person_id" type="integer">
  Meldende Person. Eine `bigint`-Sequenz aus einem anderen Subsystem — nicht als derselbe
  ID-Raum behandeln wie `person_id` auf `Accounting.booking_header` oder
  `Stakeholder.tenants`.
</ResponseField>

<ResponseField name="reporter_person" type="string">
  Name der meldenden Partei — das lesbare Gegenstück zu `person_id`. Auf wenigen Zeilen ein
  leerer String.
</ResponseField>

<ResponseField name="reporter_type" type="string">
  Art der meldenden Partei — einer der Werte `"Person"`, `"Eigentümer"`, `"Kreditor/Firma"`,
  `"Partner"`, `"iX-Haus Benutzer"`. Auf jeder Zeile befüllt.
</ResponseField>

<ResponseField name="cost_center_id" type="string">
  Kostenstelle, der die Meldung zugeordnet ist.
</ResponseField>

<ResponseField name="cost_center_id_name" type="string">
  Lesbarer Name zu `cost_center_id`. Genau ein Name pro ID — direkt anzeigbar, ohne die
  Kostenstelle nachzuschlagen.
</ResponseField>

<ResponseField name="report_type" type="string">
  Meldungsart.
</ResponseField>

<ResponseField name="priority_text" type="string">
  Priorität.
</ResponseField>

<ResponseField name="Status" type="string">
  Aktueller Status der Meldung. Das große `S` ist kein Tippfehler — das Feld heißt wirklich
  `Status`, anders als das kleingeschriebene `status` auf `projects`.
</ResponseField>

<ResponseField name="status_date" type="date">
  Datum, an dem der aktuelle `Status` gesetzt wurde. Auf jeder Zeile befüllt.
</ResponseField>

<ResponseField name="report_date" type="date">
  Datum, an dem die Meldung erstellt wurde.
</ResponseField>

<ResponseField name="to_do_period" type="object">
  Geplanter Zeitraum für die Durchführung — `{start, end}` (Datumsstrings). Beide Grenzen
  sind auf jeder Zeile befüllt.
</ResponseField>

<ResponseField name="duration_days" type="integer">
  Dauer in Tagen, auf rund einem Drittel der Zeilen befüllt. Welche zwei Daten sie umfasst,
  ist nicht dokumentiert — vor der Nutzung beim Support nachfragen.
</ResponseField>

<ResponseField name="insurance_case" type="boolean">
  Ob die Meldung mit einem Versicherungsfall verknüpft ist.
</ResponseField>

<ResponseField name="responsible_team" type="string">
  Verantwortliches Team, als numerischer Code in einem String (z. B. `"1"`, `"2"`) — **nicht**
  die lesbaren Teamnamen aus
  [`Stakeholder.employees.team`](/de/v1/data-model/stakeholder). Auf deutlich unter 2 % der
  Zeilen befüllt, also keine Zuständigkeitslogik darauf aufbauen.
</ResponseField>

<ResponseField name="responsible_user" type="string">
  Anzeigename des Benutzers, dem die Meldung zugewiesen ist. Auf der großen Mehrheit der
  Zeilen ein leerer String, und ein Teil der übrigen Werte sind technische Import-Accounts,
  keine Personen.
</ResponseField>

<ResponseField name="user_creation" type="string">
  Anzeigename des Benutzers, der die Meldung erstellt hat. Dieselben Einschränkungen wie bei
  `responsible_user`: überwiegend leer, mit technischen Accounts unter den Werten.
</ResponseField>

<ResponseField name="comment" type="string">
  Freitextkommentar, auf fast jeder Zeile befüllt.
</ResponseField>

## projects

`GET /v1/operations/projects` — Investitionsprojekte und größere Maßnahmen über mehrere
Aufträge.

<ResponseField name="project_id" type="integer" required>
  Eindeutige Projekt-ID.
</ResponseField>

<ResponseField name="project_number" type="string">
  Lesbare Projektnummer — zu unterscheiden von `project_id` oben, das für Abfragen und Joins
  zu verwenden ist.
</ResponseField>

<ResponseField name="property_id" type="string" required>
  Eindeutige Objekt-ID.
</ResponseField>

<ResponseField name="account_name" type="string">
  Beschreibung der Maßnahme, meist Gewerk plus Ort (z. B. `"Malerarbeiten"`). Trotz des Namens
  kein Name aus `Accounting.accounts` — und da es kein separates Projektnamensfeld gibt, ist
  das die Bezeichnung des Projekts.
</ResponseField>

<ResponseField name="cost_center" type="object">
  Kostenstelle, auf die das Projekt gebucht wird — `{code, label}`.
</ResponseField>

<ResponseField name="ledger_account" type="string">
  Sachkonten, auf die die Projektkosten buchen, als **kommaseparierte Liste in einem einzigen
  String** (z. B. `"641100,650100,651100"`) — kein einzelner Wert. Vor dem Abgleich mit
  `Accounting.accounts.account_number` an den Kommas trennen; jeder Teil löst sich dort auf,
  allerdings nicht immer innerhalb des Objekts des Projekts.
</ResponseField>

<ResponseField name="ledger_account_nr" type="string">
  Auf jeder befüllten Zeile identisch mit `cost_center.code` — das Feld enthält die
  Kostenstelle, keine Sachkontonummer. `cost_center` verwenden und dieses Feld ignorieren.
</ResponseField>

<ResponseField name="creditor_id" type="string">
  Hauptkreditor des Projekts. Die Werte liegen in einem anderen ID-Raum als
  `Stakeholder.creditor.creditor_id` und lösen sich dort nicht auf — nicht als Fremdschlüssel
  verwenden.
</ResponseField>

<ResponseField name="offer_id" type="integer">
  Zugehöriges Angebot, auf rund 60 % der Zeilen befüllt. `offers` hat noch keinen
  `/v1/`-Endpunkt (siehe Hinweis oben), lässt sich über `/v1/` also heute nicht auflösen.
</ResponseField>

<ResponseField name="offer_nr" type="string">
  Lesbare Nummer dieses Angebots.
</ResponseField>

<ResponseField name="report_id" type="integer">
  Zugehörige Meldung, falls das Projekt aus einer entstanden ist. Nur auf sehr wenigen Zeilen
  befüllt, und jeder befüllte Wert löst sich gegen
  [`notifications.report_id`](#notifications) auf.
</ResponseField>

<ResponseField name="report_number" type="string">
  Lesbare Nummer dieser Meldung, auf denselben wenigen Zeilen befüllt wie `report_id`.
</ResponseField>

<ResponseField name="request_hdr_id" type="integer">
  Interne ID der Anfrage, aus der das Projekt hervorgegangen ist. Auf rund 70 % der Zeilen
  befüllt und von mehreren Projekten geteilt — das Feld gruppiert Projekte, identifiziert also
  keins. Anfragen sind über keinen `/v1/`-Endpunkt abrufbar; als opaken Gruppierungsschlüssel
  behandeln.
</ResponseField>

<ResponseField name="request_nr" type="string">
  Lesbare Nummer dieser Anfrage.
</ResponseField>

<ResponseField name="to_hdr_id" type="integer">
  Trotz des Namens löst sich das Feld nicht gegen `technical_objects.to_id` auf (nur rund
  3,5 % der Zeilen treffen). Nicht als Fremdschlüssel verwenden — für die funktionierenden
  Verknüpfungen `report_id` oder `offer_id` nehmen.
</ResponseField>

<ResponseField name="to_name" type="string">
  Name des technischen Objekts, nur auf einigen Dutzend Zeilen befüllt.
</ResponseField>

<ResponseField name="hierarchy" type="string[]">
  Position in der Kostenstruktur-Hierarchie, als geordnetes Array von oben nach unten. Leere
  Ebenen werden weggelassen, die Array-Länge variiert also pro Projekt.
</ResponseField>

<ResponseField name="project_type" type="string">
  Projekttyp.
</ResponseField>

<ResponseField name="status" type="string">
  Aktueller Projektstatus.
</ResponseField>

<ResponseField name="industry_name" type="string">
  Gewerk, zu dem die Maßnahme gehört. Auf rund drei Vierteln der Zeilen befüllt.
</ResponseField>

<ResponseField name="responsible_team" type="string">
  Verantwortliches Team als lesbarer Name. Nutzt dasselbe Vokabular wie
  [`Stakeholder.employees.team`](/de/v1/data-model/stakeholder), enthält heute aber auf jeder
  Zeile `"Objektmanagement"` — das Feld unterscheidet Projekte also nicht.
</ResponseField>

<ResponseField name="responsible_user" type="string">
  Anzeigename des verantwortlichen Benutzers. Auf der großen Mehrheit der Zeilen Leerzeichen
  oder ein technischer Account.
</ResponseField>

<ResponseField name="project_period" type="object">
  Projektlaufzeit — `{start, end}` (Datumsstrings).
</ResponseField>

<ResponseField name="budget_period" type="object">
  Zeitraum, für den das Projektbudget gilt — `{start, end}` (Datumsstrings).
</ResponseField>

<ResponseField name="project_budget" type="string">
  Gesamtbudget des Projekts. Dezimalwert als String serialisiert, keine JSON-Zahl — vor
  Rechenoperationen casten. Auf rund einem Fünftel der Zeilen `0` statt `null`.
</ResponseField>

<ResponseField name="percentage_completed" type="string">
  Fertigstellungsgrad zwischen 0 und 100. Gleiche String-Serialisierung wie `project_budget`,
  auf rund drei Vierteln der Zeilen `0`.
</ResponseField>

<ResponseField name="funding_limit_obligo" type="string">
  Nicht dokumentiertes Geldfeld (Obligo, eine Mittelbindung). Auf rund einem Viertel der
  Zeilen ungleich `0`; das Verhältnis zu `project_budget` ist nicht dokumentiert — vor der
  Nutzung beim Support nachfragen.
</ResponseField>

<ResponseField name="is_value" type="string">
  Nicht dokumentiertes Geldfeld. Es ist **nicht** der Ist-Verbrauch hinter
  `percentage_completed` — das Verhältnis zu `project_budget` ergibt diesen Prozentwert nicht.
  Vor der Nutzung beim Support nachfragen.
</ResponseField>

<ResponseField name="entered_value" type="string">
  Nicht dokumentiertes Geldfeld, das auf rund sieben von zehn Zeilen denselben Betrag wie
  `is_value` enthält. Vor der Nutzung beider Felder beim Support nachfragen.
</ResponseField>

<ResponseField name="activated_value" type="string">
  Wird ausgeliefert, ist heute aber auf jeder Zeile `0`.
</ResponseField>

<ResponseField name="modernized_value" type="string">
  Wird ausgeliefert, ist heute aber auf jeder Zeile `0`.
</ResponseField>

<ResponseField name="maintenance_value" type="string">
  Wird ausgeliefert, ist heute aber auf jeder Zeile `0`.
</ResponseField>

<ResponseField name="projektleitung" type="string">
  Projektleitungs-Flag, ein `'0'`/`'1'`-String statt eines Booleans. Vor der Nutzung der
  beiden Werte beim Support nachfragen.
</ResponseField>

<ResponseField name="project_lead_budget" type="string">
  Nicht dokumentiertes Geldfeld, nur auf einigen Dutzend Zeilen ungleich `0`. Vor der Nutzung
  beim Support nachfragen.
</ResponseField>

<ResponseField name="overhead_charge_mode" type="integer">
  `0` oder `1` — ein Integer-Flag, kein Boolean. Welchen Modus welcher Wert wählt, ist nicht
  dokumentiert; vor der Nutzung beim Support nachfragen.
</ResponseField>

<ResponseField name="overhead_charge_percent" type="string">
  Umlage als Prozentwert, auf rund jeder zehnten Zeile ungleich `0`.
</ResponseField>

<ResponseField name="overhead_charge_value" type="string">
  Umlage als absoluter Betrag, nur auf einer Handvoll Zeilen ungleich `0`. Welches der beiden
  Umlagefelder greift, steuert vermutlich `overhead_charge_mode` — das aber nicht dokumentiert
  ist.
</ResponseField>

<ResponseField name="comment" type="string">
  Freitextkommentar, auf rund jeder sechsten Zeile befüllt.
</ResponseField>

<ResponseField name="comment_1" type="string">
  Weiteres Kommentarfeld, praktisch auf jeder Zeile leer — der Text steht in `comment`.
</ResponseField>

<ResponseField name="comment_2" type="string">
  Weiteres Kommentarfeld, heute auf jeder Zeile leer.
</ResponseField>

<ResponseField name="comment_3" type="string">
  Weiteres Kommentarfeld, praktisch auf jeder Zeile leer.
</ResponseField>

<ResponseField name="budget_text" type="string">
  Wird ausgeliefert, ist heute aber auf jeder Zeile leer.
</ResponseField>

<ResponseField name="budget_comment" type="string">
  Wird ausgeliefert, ist heute aber auf jeder Zeile leer.
</ResponseField>

<ResponseField name="dms_link" type="string">
  Link zum Dokumentenordner des Projekts im Dokumentenmanagementsystem. Auf jeder Zeile
  befüllt.
</ResponseField>

<Warning>
  Jedes Geldfeld auf `projects` kommt auf jeder Zeile zurück, wobei `0` für „nicht gesetzt"
  steht — es gibt keine `null`-Werte zum Filtern. Nur `project_budget` und
  `percentage_completed` haben eine dokumentierte Bedeutung; die übrigen werden so
  ausgeliefert, wie das Quellsystem sie hält, und drei davon sind durchgängig `0`. Kein
  Projekt-Finanzreporting darauf aufbauen, ohne die Definitionen vorher mit dem Support zu
  klären.
</Warning>
